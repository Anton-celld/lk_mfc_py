# SOAP-интеграция 1С — первый подготовительный этап

Этот проект сохраняет **межсервисный HTTP API** и отдельно выбирает транспорт к 1С:
`MFC_ONEC_TRANSPORT=http|soap`. В `http` продолжает работать исходный `lk/onec.py`,
в `soap` — совместимый по методам `lk/onec_soap.py`.

## Настройка

Обязательные для SOAP настройки (значения приватные, не коммитить):

```dotenv
MFC_ONEC_TRANSPORT=soap
MFC_ONEC_WSDL=https://internal.example.invalid/path/Service.1cws?wsdl
MFC_ONEC_LOGIN=technical-user
MFC_ONEC_PASSWORD=use-secret-manager
MFC_ONEC_TIMEOUT=20
MFC_ONEC_MAX_CONCURRENT=5
MFC_ONEC_CA_FILE=/path/to/internal-ca.pem
```

Технический `MFC_ONEC_USER` по-прежнему поддерживается как синоним логина;
если заданы оба, `MFC_ONEC_USER` имеет приоритет. `MFC_ONEC_CA_FILE` необязателен,
если сертификат выдан общедоверенным CA. Проверка TLS **не отключается**.
Для работы нужны: доступ к сети 1С и разрешённая техническая учётная запись
с доступом к WSDL и к SOAP endpoint. Пока предполагается HTTP Basic Auth;
если используется иной механизм, его нужно отдельно реализовать и протестировать.

Локальная установка SOAP-зависимостей:

```bash
python -m pip install -r requirements-soap.txt
```

## Сопоставление операций WSDL

Реального WSDL нет в этом архиве. Поэтому мы **не подменяем** имена операций
вымышленными. В `config.json` или `portal_config.json` нужно задать
`onec.soap.operations`. Пример **с условными названиями**:

```json
{
  "onec": {
    "transport": "soap",
    "wsdl": "",
    "soap": {
      "max_concurrent": 5,
      "operations": {
        "person": {
          "method": "METHOD_FOR_PERSON_FROM_REAL_WSDL",
          "args": {"PersonID": "$id"}
        },
        "request_create": {
          "method": "METHOD_FOR_CREATE_FROM_REAL_WSDL",
          "args": {"Request": "$payload"},
          "output_fields": {"id": "RequestID", "number": "Number", "status": "State"}
        },
        "requests_list": {
          "method": "METHOD_FOR_LIST_FROM_REAL_WSDL",
          "args": {"Since": "$since"},
          "response": "Result"
        },
        "request_document": {
          "method": "METHOD_FOR_PDF_FROM_REAL_WSDL",
          "args": {"ID": "$id"},
          "response": "FileData",
          "encoding": "base64",
          "content_type": "application/pdf"
        }
      }
    }
  }
}
```

Замените ВСЕ `METHOD_FOR_*` только после анализа настоящего WSDL.
`args` — шаблон именованных параметров, `$id`, `$payload`, `$since`,
`$program`, `$login`, `$password`, `$token`, `$reason` берутся из серверных
вызовов. Поддерживается путь `$payload.lk_id`, вложенные словари и списки.
`response` — необязательный путь к значению в SOAP-ответе.
`json_response: true` — если метод **действительно возвращает JSON-строку**.
`output_fields` — сопоставление собственных полей МФЦ с полями SOAP-ответа;
значение `"."` обозначает результат целиком (например, скалярный ID).

Полный перечень прикладных операций, ожидаемых `lk/onec.py`:

- `auth_check`, `auth_token`, `accounts` (нужны только соответствующим способам входа);
- `person`, `prikazy`, `signers`;
- `request_create`, `request_update`, `request_cancel`, `request_reject`;
- `requests_list`, `request_document`, `request_signature`.

Если метод не сопоставлен, операция **завершается явной ошибкой**; она не
переадресовывается автоматически на HTTP. SOAP должен возвращать необходимые
для существующего МФЦ структуры: например `request_create` -> `{"id": ...}`,
`requests_list` -> список или `{"requests": [...]}`, получение PDF/.sig ->
байты (либо base64 при `encoding: "base64"`). При несовместимом ответе
потребуется специальный адаптер контракта после изучения WSDL.

**Важно:** если сеть оборвалась во время `request_create` или метод создания
не вернул ID, заявка получает `sync=error`, а не `sync=queued`.
Это защита от автоматического создания дублей. Администратор должен сверить
заявку с 1С, и только затем вручную решить, повторять ли отправку.
До реальной эксплуатации нужно также согласовать идемпотентность по `lk_id`
на стороне 1С и сверку ранее созданных заявлений.

## Проверки

```bash
python -m pytest -q tests/test_onec_soap.py tests/test_portal_sso.py
```

Тесты проверяют выбор транспорта, конфигурацию, преобразование аргументов,
нормализацию ответов, бинарные файлы и безопасное поведение при неопределённом
результате создания. **Это не интеграционные тесты с реальной 1С.**

Перед вводом в работу в университетской сети проверить:

1. HTTPS/CA, DNS, маршрут к WSDL и импортируемым XSD.
2. Авторизацию отдельно на получение WSDL и POST SOAP endpoint.
3. Реальный список методов, типы параметров, структуру результата, PDF и SIG.
4. Права технической учётной записи.
5. Создание единственной заявки с известным `lk_id`, отмену и изменение.
6. Идемпотентность при повторе и обрыве соединения.
7. Обновление статусов через 1С без смены первоначального статуса ЛК.

## Общая библиотека Freontt/soap-client

Изучена https://github.com/Freontt/soap-client, версия проекта на момент
анализа — `0.1.0`. В ней уже есть zeep, Basic Auth, регистр клиентов и
ограничители, но до внедрения в МФЦ следует улучшить: TLS CA, исключение
параметров SOAP из debug-логов, асинхронную инициализацию WSDL (или запуск
синхронной в worker-thread), классификацию сетевых ошибок и освобождение
синхронного WSDL HTTP-клиента.

**Текущая сборка использует `zeep` непосредственно**, а не импортирует пакет
`soap-client`. Это осознанный совместимый временный слой до доработки
общей библиотеки. Нельзя считать, что изменения в `Freontt/soap-client`
уже выполнены или выпущены: текущий репозиторий не изменялся.

## Авторизация пользователей — отдельно

`X-Service-Token` — механизм доверия между шлюзом и микросервисами, он **не
заменяет технический Basic Auth к 1С**. Перевод МФЦ с одноразового билета BFF
на X-Service-Token в этом пакете НЕ сделан; для этого дополнительно нужны
маршрутизация через Gateway, проверка `targetService`, роль и ограничение
всех студенческих данных по выбранной зачётке. Не считать SOAP-релиз
разрешением использовать сервис с настоящими данными без этих проверок.
