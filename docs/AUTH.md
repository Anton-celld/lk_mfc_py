# Авторизация и разграничение доступа

## Реализованная схема

Сейчас вход в студенческий микросервис основан на одноразовом HMAC-SHA256 билете, выдаваемом доверенным BFF/порталом. Проверяются подпись, срок действия, `iss`, `aud`, роль `student` и уникальность `nonce`. Далее сервис создаёт собственную cookie-сессию.

Код: `lk/portal_sso.py`, `lk/auth.py`, `lk/web.py`. Детали текущего протокола: [README_PORTAL_PYTHON.md](../README_PORTAL_PYTHON.md).

**Ограничение:** текущий билет передаёт `sub` (ID физлица в 1С), но не выбранную зачётную книжку. Не считать текущую схему эквивалентной новой модели контекста ролей платформы.

## Целевая схема: X-Service-Token (ещё не реализована)

Планируется перевести сервис на вход через Gateway. Gateway проверяет пользовательскую сессию и выбранный контекст роли, удаляет клиентские `X-User-*` и выдаёт подписанный, короткоживущий `X-Service-Token` для конкретного микросервиса.

Сервис обязан:
- проверять подпись и строго разрешённый алгоритм, срок действия, `targetService` и другие обязательные ограничения выданного токена;
- брать роль и `identifier` только из проверенного токена;
- для студента требовать `activeRole=student`, `identifierType=recordbook` и непустую зачётку;
- не принимать номер зачётки из query/body/path как источник полномочий;
- ограничивать по зачётке **каждый** запрос к программам, заявлениям, файлам, подписям и истории, включая прямые ссылки;
- если выбран режим «Все роли» или номер отсутствует, возвращать понятный отказ (например, `409` с предложением выбрать зачётку), а не раскрывать все программы;
- не кэшировать пользовательский контекст независимо от проверенного токена;
- не допускать вызовов в обход доверенного шлюза и не логировать номера полностью.

ID физлица `sub` и номер зачётки `identifier` имеют разные задачи: первый идентифицирует человека, второй определяет выбранную область данных.

## Переход

Сначала реализовать проверку токена и строгую выборку по зачётке, написать негативные тесты (две зачётки у одного студента, смена роли, отсутствующий номер, подделанный заголовок, прямые ссылки на чужие документы). Затем испытать новую маршрутизацию со шлюзом на стенде. Только после успешной проверки выводить из эксплуатации билетный вход.

**Технический логин и пароль к SOAP/WSDL 1С — отдельный секрет сервера.** Они никогда не должны передаваться пользователю или вкладываться в `X-Service-Token`.

В исходном `microservices-roles.md` платформы указана модель `X-Service-Token`; этот файл пока не является частью данного репозитория. Перед реализацией требуется сверить актуальную версию контракта шлюза.
